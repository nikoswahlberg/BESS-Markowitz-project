# Project blueprint

Living reference for the structure and open modelling decisions of the BESS
reserve market allocation project. Update this file when a decision is made or
the layout changes; `CLAUDE.md` holds the conventions and hard constraints.

Last updated: 2026-09-28 (fetch layer built, study period set, raw data report)

## Goal

Fetch Finnish reserve market prices (FCR-N, FCR-D up/down, aFRR) from the
Fingrid open data API and day-ahead prices from ENTSO-E, estimate their
covariance, and allocate a 30 MW battery's capacity across markets by
mean-variance and mean-CVaR.

**Study period:** 2026-01-01 to 2026-06-30 inclusive, Finnish local time
(Europe/Helsinki), set in `config/study.toml`. That is 4343 hours: 181 days
minus the spring-forward hour on 2026-03-29.

## Design principles

- **Four layers that only depend downward:** `fetch → prep → estimation → optimize`.
  Only `fetch/` talks to the network or needs API keys. Everything after it is a
  pure function on DataFrames, so it can be tested without keys.
- **The domain constraints live in one place.** `optimize/constraints.py` holds
  the three rules: the 30 MW cap, no selling the same MW twice, and FCR-N
  symmetry. Both the mean-variance and mean-CVaR code import them, so the two
  models can't drift apart. Each rule has a test that should fail when the rule
  is broken.
- **Moments and scenarios are kept separate.** Mean-variance uses μ and Σ from
  `moments.py`; mean-CVaR uses the scenario matrix from `scenarios.py`. Both
  derive from the same processed panel.
- **Test fixtures:** synthetic data is only used where a test needs a known
  answer, and is labelled as synthetic. The Fingrid parsing test uses a real
  response saved once, not a made-up one.
- **Notebooks stay thin** because every step they need has a function in `src/`.

## Open decisions

Settle these before writing optimization code. When one is decided, move it to
the decision log below with the choice and the reason.

1. **What counts as double-selling?** A battery can physically hold the same MW
   in reserve for both FCR-D up and FCR-D down. Read literally, the rule in
   `CLAUDE.md` forbids that. One shared 30 MW budget, or separate budgets for up
   and down? Affects `constraints.py` and how FCR-N symmetry is expressed.
2. **Is the day-ahead spread a capacity market?** It's energy arbitrage, so it
   depends on energy capacity (MWh), state of charge and round-trip efficiency,
   not just MW. Treating it as another asset priced in €/MW/h is a
   simplification. `battery.toml` needs an energy capacity either way, and
   `CLAUDE.md` doesn't give one.
3. **One allocation or one per hour?** A single allocation over the whole
   history is classic Markowitz. Separate allocations per hour of the day (or
   per season) add a grouping step in `estimation/` and a loop in `optimize/`.
4. **ENTSO-E env var name.** `CLAUDE.md` and the code use `ENTSOE_TOKEN`; the
   local `.env` currently names it `ENTSOE_API_KEY`. Rename one to match.
5. **Day-ahead resolution in prep/.** Finnish day-ahead is PT60M before delivery
   day 2025-10-01 and PT15M from then on, while reserve prices are hourly. Decide
   whether prep/ averages 15-min day-ahead prices to hourly or keeps 15-min for
   the spread calculation.
